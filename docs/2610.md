> NRVO

함수 안에서 만든 지역 변수를 값으로 반환할 때는 `std::move`를 붙여야
복사 비용을 줄일 수 있을 것처럼 보인다. 

지역 변수 `s`는 lvalue이고 함수가 끝나면 소멸하기 때문이다. 

하지만 `return s;`처럼 지역 변수의 이름을 그대로 반환하면, 
컴파일러는 호출자가 받을 결과 객체의 저장 공간에 `s`를 직접 생성할 수 있다. 
이를 NRVO(Named Return Value Optimization)라고하며, 
복사나 이동 자체가 생략되므로 `std::move(s)`를 붙일 필요가 없다.

반대로 `return std::move(s);`처럼 
반환식이 단순한 변수 이름이 아니면 NRVO의 대상이 되지 않을 수 있고, 
그 경우에는 `s`를 이동한 뒤 지역 객체를 소멸시키는 추가 작업이 필요해질 수 있다. 

따라서 반환할 지역 변수라면 먼저 `return s;`를 사용하고, 실제로 복사나 이동이 발생하는지와 성능을
프로파일링하는 것이 좋다. 

다만 NRVO는 모든 반환식에 적용되는 것은 아니며, 서로 다른 지역 변수를 조건에 따라 반환하는 경우처럼 
컴파일러가 하나의 객체로 합치기 어려운 상황에서는 적용되지 않을 수 있다.

```cpp
#include <utility>

struct Widget {
    Widget();
    Widget(const Widget&); // 복사 생성자
    Widget(Widget&&);      // 이동 생성자
};

Widget make_widget()
{
    Widget w;
    return w;              // NRVO가 적용될 수 있음
}

Widget make_widget_with_move()
{
    Widget w;
    return std::move(w);   // NRVO가 적용되지 않을 수 있음
}
```

두 함수 모두 문법적으로는 `Widget`을 반환하지만, 첫 번째 함수에서는
호출자의 결과 객체가 만들어질 공간에 `w`를 직접 생성할 수 있다. 

두 번째 함수에서는 `std::move(w)`가 `w`를 xvalue로 변환하므로 이동 생성이
선택될 수 있지만, 이것은 NRVO와는 다른 동작이다. 

또한 반환 대상이 `Widget`처럼 이동 비용이 큰 타입이라면 `std::move`가 성능을 개선하기보다
오히려 NRVO를 막아 성능을 떨어뜨릴 수 있다.

> RAII

예전에는 동적으로 할당한 메모리나 운영체제 자원(파일, 뮤텍스 등)을
개발자가 직접 해제해야 했다. `new`로 얻은 메모리는 `delete`로,
열어 둔 파일은 `close`로, 잠근 뮤텍스는 `unlock`으로 반환해야 하는 식이다.
이런 해제를 놓치면 더 이상 사용하지 않는 자원이 계속 점유되는
메모리 누수(memory leak)나 자원 누수가 발생한다. 누수가 반복되면 사용
가능한 메모리가 줄어들고, 결국 성능 저하나 메모리 고갈(OOM)로 이어질 수
있다. 메모리 스와핑은 메모리가 부족할 때 운영체제가 메모리와 저장 장치
사이에서 페이지를 옮기는 현상이고, 메모리 누수 그 자체와는 구분해야 한다.
또한 힙 언더플로우는 메모리 누수와 다른 오류다. 일반적으로 할당한
버퍼의 앞부분을 잘못 접근하는 문제를 가리키며, 여기서 말하는 문제는
메모리 고갈 또는 OOM에 가깝다.

```cpp
#include <iostream>
#include <string>

void print_message()
{
    auto* message = new std::string("hello");
    std::cout << *message << '\n';

    delete message; // 이 줄을 빠뜨리면 메모리 누수
}
```

작은 함수에서는 해제를 잊지 않을 수 있지만, 예외가 발생하거나 함수가
여러 경로로 종료되면 모든 경로에서 `delete`를 호출하기가 어려워진다.
예를 들어 다음 코드에서 `do_something()`이 예외를 던지면 `resource`를
해제하는 코드에 도달하지 못한다.

```cpp
struct Resource {};
void do_something();

void use_resource()
{
    auto* resource = new Resource();
    do_something();       // 예외가 발생할 수 있음
    delete resource;      // 예외가 발생하면 실행되지 않음
}
```

이 문제를 해결하는 핵심 아이디어가 RAII(Resource Acquisition Is
Initialization)다. 자원의 획득과 해제를 객체의 생성과 소멸에 연결하는
방식이다. 객체는 자신이 속한 scope에 들어갈 때 자원을 획득하고, scope를
벗어날 때 소멸하면서 자원을 자동으로 반환한다. 따라서 정상적으로
끝나는 경우뿐 아니라 예외로 scope를 빠져나가는 경우에도 정리 작업이
수행된다.

```cpp
#include <memory>

struct Resource {};
void do_something();

void use_resource()
{
    auto resource = std::make_unique<Resource>();
    do_something(); // 예외가 발생해도 resource의 소멸자가 호출됨
}                  // 여기서 Resource가 자동으로 해제됨
```

`std::unique_ptr`는 대표적인 RAII 도구다. 특별한 소유권 공유가 필요하지
않다면 `new`와 `delete`를 직접 사용하는 대신 `std::make_unique`로 객체를
만들고, 소유권이 하나라는 사실을 타입으로 표현하는 것이 좋다. 여러
객체가 하나의 자원을 함께 소유해야 할 때는 `std::shared_ptr`를 사용할
수도 있지만, 소유권 관계가 복잡해질 수 있으므로 먼저 `unique_ptr`나
일반 지역 객체처럼 더 단순한 방법을 고려하는 편이 좋다.

```cpp
void write_file()
{
    std::ofstream file("result.txt");
    file << "hello\n";
} // scope를 벗어나면 ofstream의 소멸자가 파일을 자동으로 닫음
```

즉 RAII는 메모리에만 적용되는 기법이 아니다. 파일, 락, 소켓처럼
사용이 끝난 뒤 반드시 반환해야 하는 모든 자원에 적용할 수 있다. C++에서는
자원의 수명을 객체의 수명과 일치시키면 개발자가 모든 종료 경로를 직접
관리해야 하는 부담과 자원 누수 가능성을 줄일 수 있다.
